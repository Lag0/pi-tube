# Testing the npm-installed command

On 2026-11-24, [audit finding 7](https://github.com/Lag0/pi-tube/issues/31#issuecomment-7147696990) distinguished two failures: Node might not find a native Bun executable on `PATH`, or npm's installed `pi-tube` launcher might not work. Running the checkout's `bin/pi-tube.ts` through Bun does not test the launcher. A historical Windows `ENOENT` did not establish that Bun 1.4.5 or the npm launcher was incompatible.

[Lag0/pi-tube@9a0ddf6](https://github.com/Lag0/pi-tube/commit/9a0ddf6) merged [PR #65](https://github.com/Lag0/pi-tube/pull/65) for [spec #62](https://github.com/Lag0/pi-tube/issues/62) and [ticket #63](https://github.com/Lag0/pi-tube/issues/63). On reviewed head `81598ae`, the [Windows, macOS and Ubuntu jobs](https://github.com/Lag0/pi-tube/actions/runs/45511382163) verified native Bun lookup separately and ran npm's generated command from outside the checkout. Each installed a locally packed tarball into a temporary prefix, then checked help, the installed version and credential-free provider status. Dependency installation could fetch public packages, with lifecycle scripts disabled. Nothing was published; this did not test registry availability, global PATH setup, a Node-only runtime or paid transcription. Both delivery issues closed; the wider audit remained open for cleanup safety.

The current Windows smoke separately imports the installed binary runner under Bun, starts the known absolute Node runtime, and compares synthetic stdin and stdout byte for byte. The installed CLI help/version/provider checks alone do not exercise that native path. Neither check invokes a downloader or a paid provider.

The installed smoke also imports the page-audio validator under Bun and checks a synthetic MP3 through its packed TypeScript worker. Separate abort, timeout and message-free exit cases substitute controlled worker bodies only in the temporary install. They exercise the real worker runtime and parent cleanup, not performance under a large media load.
