## Current checkout: manual audio cleanup is unavailable

`library prune` without `--include-transcripts` no longer scans or removes audio on any platform, including Windows. An `audio.*` name, age, size or identical contents do not establish that pi-tube created the current file. `keepAudio` does not yet record independent evidence of the version it published. Preview and apply therefore report zero selected or removed, **not** zero audio usage. JSON reports `unsupported: true` and `reason: "unverified_audio_ownership"`; a configured space target is returned as `max_audio_bytes` with `cap_verified: false`. Apply is still audited.

This fence does not deliver verified manual reclaim (#34) or change transcript cleanup (#33). It did not change eviction or replacement during retention. Do not use a library containing personal files for audio retention. No files are migrated or adopted.

### Automatic space cap during retention

A successful keep with `library.max_audio_bytes` reports `audio_cap: "unenforced"` in CLI JSON and MCP, or a warning on CLI stderr. No overflow scan or eviction runs. Disk usage can grow; this is not a measurement of usage or a claim that the target was exceeded. A warning does not invalidate the transcript or require another provider call.

This fence does not complete #35 or #68. On the unchanged POSIX path, keeping audio for the same source can still delete an alternate-extension sibling or overwrite an occupied name. There, `storedSource` still reuses audio by filename, not by proof of creation. Safe replacement and reuse need evidence captured at publication and input bound to the verified object through consumption. Keep personal files outside the library.

### First retained copy on Windows (#68, partial)

On capable local Windows volumes, keeping a fresh page download stages a private copy on the **destination** volume. Publication renames the opened stage without replacement into a verified directory. An existing `audio.*` is left alone; CLI JSON and MCP report `audio_retention: "kept"` for a published Windows copy, `"skipped"` for a safe refusal or `"incomplete"` for an I/O failure. The latter two produce a warning in human CLI output. Transcription uses the validated private audio (the private M4A remux for a transport stream), not the retained pathname. There is no fallback to overwriting rename. A successful keep with a cap still reports `audio_cap: "unenforced"`.

There is no durable audio receipt: neither this copy nor a matching name or digest authorizes later deletion. Windows therefore downloads again on a transcript miss rather than sending an unverified library file to a provider. Transcript cache hits still need no download or paid call. Verified reuse, replacement, and eviction remain open. POSIX retention and its filename-based reuse are unchanged, **not** covered by these Windows guarantees; keep personal files out of the library.

### Concurrent Windows publication (#68)

Under the [#68 owner decision](https://github.com/Lag0/pi-tube/issues/68#issuecomment-7175587952), an `audio.*` found in the pre-scan still skips the keep. If a writer adds a different extension after the scan, both files may survive. An occupied exact destination is never replaced. On success CLI JSON and MCP report `retained_audio_path` from this publication only; the other file is neither adopted nor used for STT. A skipped keep or transcript cache hit reports no retained path.

Windows page fetches create a private directory in the configured location or, if unavailable, under the verified local application-data folder. Page STT takes binary stdout, not a downloader-reported pathname. Cleanup marks only app-created, pinned media and the empty created directory for deletion by handle. Unknown or unremovable residue produces a warning, not recursive deletion or loss of the provider result.

On POSIX the existing file-based yt-dlp selection, handoff and cleanup are unchanged. The Windows draft checks parsed track information against MP3 frame boundaries, WebM element extents and audio blocks, or MP4 box extents and sample-byte totals. One audio track may accompany video; video is not removed. These checks do not establish that all source fragments arrived, that every sample decodes, or that the recording is authentic. Retention takes the original producer output. For supported AAC transport streams FFmpeg stream-copies to a different MP4 container for validation and upload; the files are not byte-identical.

**Format parity: BLOCK.** The unchanged `bestaudio[ext=m4a]/bestaudio/best` selector can choose more than audio-only M4A. Verified Windows fixtures include MP3; single-stream Ogg/Opus (lacing, sequence, EOS and page CRC); native FLAC (metadata bounds, frame CRCs and declared sample totals); RIFF/WAVE integer PCM (chunk extents and frame alignment); AAC and ALAC in M4A; Opus and Vorbis in WebM (including an unknown-length Segment); H.264/AAC MP4 and VP9/Opus WebM with video intact. Their original bytes go to the provider. AAC TS (including H.264 video) requires a successful stream-copy remux; retention still gets TS, not MP4.

The old file handoff used the producer's filename. Groq takes a named upload and lists MP3, MP4, M4A and WebM among its accepted formats; ElevenLabs takes a named file and documents major audio **and video** formats. Deepgram receives the buffer, not a filename. None of these adapters selects an audio track. This is not a guarantee that every codec in a recognized container will be accepted remotely.

Groq�s [transcription API](https://console.groq.com/docs/api-reference#audio-transcription) also lists `mpeg` and `mpga`; the Windows MPEG audio path only validates Layer III. An MPEG program stream is not an MP4 box stream or an AAC transport stream and remains gated. Other product-recognized inputs still outside this slice include QuickTime MOV (`qt` brand) and elementary AAC/ADTS; neither is the supported AAC-in-TS remux. A listed upload format is not evidence for every codec combination. The direct-source extension list is not a provider capability matrix.

The old handoff passed multiple audio tracks through together: it did not select a language, strip tracks, or guarantee which one a provider transcribed. Windows still refuses files with multiple distinct audio tracks. The outstanding decision is whether to preserve all tracks and leave interpretation to the provider, or require explicit track selection (and specify who selects and what happens when no choice is made). Refusal is not an approved narrower product contract; format parity remains blocked and #68 remains open.

**Windows binary process lifetime.** Binary acquisition creates each launcher in an owned kill-on-close Job Object with `CreateProcessW` and `PROC_THREAD_ATTRIBUTE_JOB_LIST`. Only the three standard I/O handles may be inherited. The job stays owned while both pipes drain; cancellation and deadline still apply after launcher exit. Setup or teardown failure does not authorize upload.

**TS retention conflict (#68).** Preserve the incumbent and report a skipped keep. STT may use the validated lossless stream-copy remux of this fresh download, never the incumbent. A successful TS keep retains the original TS bytes, not the remux.

MP3 validation checks frame boundaries and available Xing/Info and version-1 VBRI totals, not unknowable source completeness.

The validator counts bytes **after** the version-1 VBRI metadata frame, following [AndroidX VbriSeeker](https://github.com/androidx/media/blob/46578ee0a6/libraries/extractor/src/main/java/androidx/media3/extractor/mp3/VbriSeeker.java). For Xing/Info it includes the metadata frame in the byte count. In both cases it compares the declared frame count with the number of following audio frames. A mismatch is grounds to decline upload, even for an [otherwise playable file](https://github.com/androidx/media/issues/1904). This check does not validate the seek table.

### Manual transcript cleanup (#33)

`library prune --include-transcripts --older-than N` previews; `--yes` rechecks before applying. This backend can remove unchanged, old, individually receipted artifacts on Windows drive-letter paths on local fixed or removable volumes advertising POSIX unlink/rename support. Every ancestor must be pinnable without following a reparse point; deletion must succeed by disposition on the authorized handle. Windows alone is not a capability guarantee. A busy library is skipped, and an unexpected I/O failure is reported separately from preservation.

The current Linux and macOS backend preserves everything. Windows UNC roots, other non-drive roots, other drive types and volumes without the required flag are unsupported. Unsupported preview and apply select/remove nothing and report zero bytes. There is no pathname-unlink fallback. A link or junction is not authority to clean its target; multiply linked files (including metadata) are not selected for removal.

A legacy directory needs no migration for entries with valid independent receipts. Without that evidence even a familiar name and matching contents cannot distinguish an original from a replacement. Edited and unreceipted entries stay. Only an empty owned directory can go; the library root stays. Bytes are logical file lengths, including `source.json` only when removed, not volume free-space measurements. The transcript-file count excludes metadata. None of these guarantees authorize audio cleanup, eviction or replacement (#34–36).
