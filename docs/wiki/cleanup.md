## Current checkout: manual audio cleanup is unavailable

`library prune` without `--include-transcripts` no longer scans or removes audio on any platform, including Windows. An `audio.*` name, age, size or identical contents do not establish that pi-tube created the current file. `keepAudio` does not yet record independent evidence of the version it published. Preview and apply therefore report zero selected or removed, **not** zero audio usage. JSON reports `unsupported: true` and `reason: "unverified_audio_ownership"`; a configured space target is returned as `max_audio_bytes` with `cap_verified: false`. Apply is still audited.

This fence does not deliver verified manual reclaim (#34) or change transcript cleanup (#33). It did not change eviction or replacement during retention. Do not use a library containing personal files for audio retention. No files are migrated or adopted.

### Automatic space cap during retention

A successful keep with `library.max_audio_bytes` reports `audio_cap: "unenforced"` in CLI JSON and MCP, or a warning on CLI stderr. No overflow scan or eviction runs. Disk usage can grow; this is not a measurement of usage or a claim that the target was exceeded. A warning does not invalidate the transcript or require another provider call.

This fence does not complete #35 or #68. Keeping audio for the same source can still delete an alternate-extension sibling or overwrite an occupied name. `storedSource` still reuses audio by filename, not by proof of creation. Safe replacement and reuse need evidence captured at publication and input bound to the verified object through consumption. Keep personal files outside the library.

### First retained copy on Windows (#68, partial)

On capable local Windows volumes, keeping a fresh page download stages a private copy on the **destination** volume. Publication renames the opened stage without replacement into a verified directory. An existing `audio.*` is left alone; CLI JSON and MCP report `audio_retention: "kept"` for a published Windows copy, `"skipped"` for a safe refusal or `"incomplete"` for an I/O failure. The latter two produce a warning in human CLI output. Transcription uses the validated private audio (the private M4A remux for a transport stream), not the retained pathname. There is no fallback to overwriting rename. A successful keep with a cap still reports `audio_cap: "unenforced"`.

There is no durable audio receipt: neither this copy nor a matching name or digest authorizes later deletion. Windows therefore downloads again on a transcript miss rather than sending an unverified library file to a provider. Transcript cache hits still need no download or paid call. Verified reuse, replacement, and eviction remain open. POSIX retention and its filename-based reuse are unchanged, **not** covered by these Windows guarantees; keep personal files out of the library.

### Draft Windows publication blocker (#68)

The current no-replace file rename protects its exact name, not a different `audio.*` extension. A directory scan and cooperating-writer lock do not exclude other writers through commit. In a disposable NTFS probe, renaming a complete new directory with an open child failed. Closing the child would lose the proof that the staged bytes remained unchanged; a user-private ACL alone does not exclude another same-user process. No directory-publisher experiment is shipped. Publication remains blocked, including an owner decision on any future policy that skips first keeps in existing transcript-only directories.

Windows page fetches create a private directory in the configured location or, if unavailable, under the verified local application-data folder. Page STT takes binary stdout, not a downloader-reported pathname. Cleanup marks only app-created, pinned media and the empty created directory for deletion by handle. Unknown or unremovable residue produces a warning, not recursive deletion or loss of the provider result.

On POSIX the existing file-based yt-dlp selection, handoff and cleanup are unchanged. The Windows draft checks parsed track information against MP3 frame boundaries, WebM element extents and audio blocks, or MP4 box extents and sample-byte totals. One audio track may accompany video; video is not removed. These checks do not establish that all source fragments arrived, that every sample decodes, or that the recording is authentic. Retention takes the original producer output. For supported AAC transport streams FFmpeg stream-copies to a different MP4 container for validation and upload; the files are not byte-identical.

**Format parity: BLOCK.** The unchanged `bestaudio[ext=m4a]/bestaudio/best` selector can choose more than audio-only M4A. Verified Windows fixtures include MP3; AAC and ALAC in M4A; Opus and Vorbis in WebM (including an unknown-length Segment); H.264/AAC MP4 and VP9/Opus WebM with video intact. Their original bytes go to the provider. AAC TS (including H.264 video) requires a successful stream-copy remux; retention still gets TS, not MP4.

The old file handoff used the producer's filename. Groq takes a named upload and lists MP3, MP4, M4A and WebM among its accepted formats; ElevenLabs takes a named file and documents major audio **and video** formats. Deepgram receives the buffer, not a filename. None of these adapters selects an audio track. This is not a guarantee that every codec in a recognized container will be accepted remotely.

Ogg/Opus, FLAC and PCM/WAV can be legitimate `bestaudio` results, but the Windows draft returns `DOWNLOAD_FAILED` before dispatch instead of handing them through. A file with two audio tracks is separately ambiguous: preserving both does not specify which language/track the provider will transcribe, and silently picking one would change the product. Release needs broader validation or an explicit product decision about those inputs. No narrower Windows contract is approved; #68 remains open.

**Windows binary process lifetime.** Binary acquisition creates each launcher in an owned kill-on-close Job Object with `CreateProcessW` and `PROC_THREAD_ATTRIBUTE_JOB_LIST`. Only the three standard I/O handles may be inherited. The job stays owned while both pipes drain; cancellation and deadline still apply after launcher exit. Setup or teardown failure does not authorize upload. The format, publication and #33 blockers are independent.

**Outstanding #68 owner interpretation.** On a TS keep conflict the incumbent sibling is preserved. The provider receives the validated stream-copy remux, not that sibling or the original TS bytes. This differs from the literal “original bytes” fallback wording; it does not amend the issue or establish approval. MP3 validation checks frame boundaries and available Xing/Info totals, not unknowable source completeness.
