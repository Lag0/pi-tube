# Library metadata scans

On 2026-11-24, [spec #56](https://github.com/Lag0/pi-tube/issues/56) addressed the number of simultaneous reads during one scan, not the number of reads needed for a page. Previously the [store at `329626c`](https://github.com/Lag0/pi-tube/blob/329626c/src/infrastructure/library/file-library-store.ts#L699-L721) collected every full transcript before projecting metadata. [Lag0/pi-tube@1f61be4](https://github.com/Lag0/pi-tube/commit/1f61be4) merged [PR #58](https://github.com/Lag0/pi-tube/pull/58): read one candidate, keep its metadata if valid, then advance. The regression observed four active candidate reads before and one after, with all four visited. The [CI run on reviewed head `7c3c7a4`](https://github.com/Lag0/pi-tube/actions/runs/45505983667) passed on Windows, Ubuntu and macOS. #56 and [#57](https://github.com/Lag0/pi-tube/issues/57) were closed.

In the [PR benchmark](https://github.com/Lag0/pi-tube/pull/58), three fresh Windows Bun 1.3.3 processes per implementation listed a one-entry page from the same 60 synthetic transcripts (6,782,180 bytes). Median process-lifetime peak RSS fell from 253,160 to 197,748 KiB; median list-call time rose from 38.27 to 70.61 ms. The baseline ran first and filesystem caches were uncontrolled. These figures are not a universal speed or memory guarantee.

A small page still visits all candidates and retains metadata for all valid entries. Search matches metadata, not transcript bodies. At this merge `total` counted valid matches; skipped candidates and unreadable directories were not reported separately. [Audit finding 6 remains partial](https://github.com/Lag0/pi-tube/issues/31#issuecomment-7146963237).

`library list` and `library search` accept `--scan-diagnostics` (MCP: `scan_diagnostics: true`). `skipped_candidates` counts enumerated candidate files whose read ended without a validated transcript. `unlisted_children` counts observed root children whose contents could not be listed, including children that disappeared. Both apply to the whole invocation, before filters and paging. `total` still counts only valid matches, and search still examines metadata, not transcript text. Neither counter estimates missing matches or unseen files; even two zeros do not guarantee a complete snapshot.
